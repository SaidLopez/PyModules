# Full-stack frontend: codegen-driven JS ecosystem, hybrid HTMX + SPA

PyModules has been a backend framework. The `pymodules.contrib.api` layer exposes `Command`-claimants as REST endpoints, but the rendering layer — what the browser actually shows — has been the user's problem. The vision driving this work is the lego-block model applied to *both halves*: install `@pymodules/auth` on the JS side and get a login UI; install `@pymodules/users` and get a user-management view. A new full-stack contrib package and a paired JS ecosystem realise this.

Several decisions taken here are independent enough to deserve separate ADRs as the system matures (outbound-policy filtering, auth transport, routing model, SEO strategy). They are bundled because they were taken in one coherent design pass and would individually leave too many dangling references in `CONTEXT.md`. Each may be split out when concrete pressure justifies it.

## Decision

**Codegen at build time, from OpenAPI and AsyncAPI.** Backend `Commands` already produce OpenAPI via FastAPI (the existing `pymodules.contrib.api` router). A new emitter produces AsyncAPI for `Events` published by Modules. A `pymodules generate` CLI reads both specs and emits typed TypeScript stubs into the consumer project. Runtime manifest fetch and a PyModules-specific manifest format were rejected: standards-aligned codegen reuses existing tooling (`openapi-typescript`, `asyncapi-generator`) and gives compile-time type safety. The cost is a build step in consumer projects and types that lag the backend until regenerated.

**Vanilla Web Components + Lit (~5 KB) for the UI layer.** Per-module npm packages ship custom elements (`<pm-login-form/>`, `<pm-user-list/>`) defined using Lit's reactive-property model. React/Vue/Svelte were rejected to keep lego blocks consumable from *any* host application — a custom element drops into React, Vue, Svelte, or plain HTML unchanged. Pure-vanilla (no helper at all) was rejected to avoid each module reimplementing reactivity. Lit is a stable Google project with a ~5 KB footprint and no build step required to use.

**SSE for backend → browser push; HTTP for browser → backend dispatch.** WebSocket was rejected for v1: SSE's `EventSource` API gives auto-reconnect for free, traverses proxies cleanly, and dispatch direction is fine over plain HTTP. Two simple channels rather than one full-duplex one. Streaming workloads (LLM token streams, live cursors) can later upgrade to WS per-feature without rewriting the rest.

**Deny-by-default outbound policy for SSE.** Each backend `Module` that publishes an `Event` registers a per-Event-class outbound policy `(event, client_context) -> bool` declaring which connected clients receive it. A browser subscribing to an unpolicied Event receives an HTTP 400 from the SSE subscription endpoint — fail loud, fail early. The policy registry lives in the full-stack contrib, **not in the `EventBus`** (preserving ADR-0007's "no middleware on the bus"). Silent-drop was rejected because forgetting a policy becomes an invisible bug; convention-based filtering (e.g., auto-match on a `user_id` field) was rejected because it couples filtering to field naming and breaks on rename.

**HttpOnly cookies, SameSite=Strict, access + refresh tokens for JS-side auth.** The browser's `EventSource` API cannot send custom headers, so a bearer-JWT-in-`localStorage` model would force a second auth path (one-time ticket exchange) for SSE alone — two auth paths to maintain forever. Cookies are sent on both channels automatically and resist XSS exfiltration; SameSite=Strict handles CSRF for first-party flows. The existing `JWTAuthProvider` is unchanged; a small FastAPI shim extracts the JWT from the cookie before `AuthMiddleware` runs.

**Module-contributed routing.** A frontend module exports `routes: [...]`; `app.register(module)` composes routes across modules into one client-side router. Mirrors `host.register(module)` on the backend — same word, same shape, both halves. File-based routing (Next.js/SvelteKit style) was rejected because it requires a build tool incompatible with shipping plain `.js` npm packages. Config-based (user writes a top-level routes file) was rejected because it duplicates the module list and routes diverge on rename. No top-level `<pm-app/>` custom element — `app.mount("#app")` renders into a normal DOM node, keeping global CSS in scope.

**Per-module layouts (one optional `layout` component per module).** Hierarchical Remix-style nested layouts were rejected for v1 as over-engineered for the common case ("all `/users/*` routes share a sidebar"). The shape chosen does not preclude adding hierarchy later when concrete demand appears.

**Hybrid HTMX + SPA for SEO.** A pure-SPA model leaks SEO: initial HTML is empty, OG tags absent for non-JS crawlers, social-media unfurls broken. Lit SSR (`@lit-labs/ssr` + Declarative Shadow DOM) was rejected because it requires a Node runtime alongside Python, doubling the deploy story. The chosen model: server-rendered HTML via Jinja2 + a new `@hx_endpoint` decorator for public / SEO-sensitive routes; the SPA layer (Web Components + Lit, codegen, SSE) for authenticated app interiors. The same backend `Command` class may carry both `@api_endpoint` (JSON, for the SPA) and `@hx_endpoint` (HTML fragment, for HTMX); purely static pages declare `@hx_endpoint` alone with no Command class. Content negotiation via `Accept` header was rejected as too magical for the project's "explicit declaration" values.

## Consequences

- A new contrib package, working name `pymodules.contrib.fullstack`, materialises. It depends on Jinja2 (template engine) and emits AsyncAPI in addition to the FastAPI-provided OpenAPI. It vendors HTMX (~14 KB) as a JS asset for HTMX routes.
- A paired npm scope (final name TBD, e.g. `@pymodules/*`) hosts per-module JS packages. **Lockstep release discipline becomes a long-term maintenance commitment** — when a `Command` shape changes on the Python side, the matching TS package must ship a new version. The project doubles its language surface (Python + TypeScript) and its package-ecosystem surface (PyPI + npm).
- The `pymodules generate` CLI is a new shipped tool. It reads the host's emitted OpenAPI + AsyncAPI, runs the chosen codegen backends, and emits typed stubs into the consumer project's source tree.
- The lego-block claim, previously confined to backend Modules, now spans both halves. Each contrib has a corresponding npm package; the two are released together.
- "Foundation of any project" is now an honest claim for application interiors *and* SEO-light front-of-funnel content — the HTMX path covers public pages without leaving the framework. The framework no longer assumes the user separately runs a marketing-site stack, though that remains a valid choice.
- Each Module that publishes any `Event` must register an outbound policy if that Event is ever to reach a browser, or accept that it remains backend-only. A registered policy with no SSE consumer is harmless; an unregistered policy with an SSE consumer is a 400. There is no quiet middle ground.
- Existing examples and tests gain a new layer: end-to-end tests must exercise the full-stack contrib alongside the existing API/DB/messaging contribs.
- This ADR does **not** specify: the final npm scope name, the static-prerendering escape hatch for `:slug`-style dynamic pages (deferred to a follow-up), SSR for the SPA layer (rejected), nested hierarchical layouts (deferred), or a `localStorage`-bearer alternative auth transport (rejected). Each is a future possible follow-up if concrete demand appears.
